Lesson 0002 · 20 minutes

Make the server stop when the client gives up

A deadline is not only a client timeout. It is the budget for the work triggered by that RPC. This experiment lets you watch that contract end on both sides.

Lesson 0001 · client card · official deadline guide

Predict before editing

Your client gives Greet two seconds. The server needs three seconds before it can reply.

t = 0s     client sends Greet, deadline is t = 2s
t = 0–2s   server is doing work
t = 2s     client stops waiting and returns DeadlineExceeded
t = 2s+    server context is cancelled

The server does not get extra time just because it is still busy. It must notice ctx.Done() and stop its own work. gRPC cannot safely stop arbitrary goroutines for you.

Change one method

Replace only the body of greetingServer.Greet. Rename the first parameter from _ to ctx. Then wait in a select with two cases:

CaseReturn
<-time.After(3 * time.Second)The normal greeting response.
<-ctx.Done()nil, ctx.Err()

Add the time import. Do not change the client’s two-second timeout.

Run the experiment

  1. Start the server: mise exec -- go run ./cmd/server.
  2. Run the client in another terminal: mise exec -- go run ./cmd/client.
  3. Record the client status and the server error returned from ctx.Err().

The client should report DeadlineExceeded. The server normally observes context canceled. Those differ because the client’s local deadline expires, then the cancellation reaches the remote handler.

Retrieval check

Which object tells the server that it should stop work?

What this means at work

For a database query, outbound RPC, loop, or channel receive started to serve a request, pass the request context down and select or check it at a natural interruption point. A deadline only saves resources if downstream work observes cancellation.
