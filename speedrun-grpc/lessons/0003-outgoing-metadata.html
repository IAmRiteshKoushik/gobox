Lesson 0003 · 20 minutes

Attach request metadata, then prove it arrived

Metadata travels beside an RPC. Use it for transport context such as request IDs and credentials, not fields that define the business request.

Lesson 0002 · client card · official metadata guide

Keep these separate

Belongs in the protobuf requestBelongs in metadata
The name that the greeting service must greet.A request ID used to correlate logs.
Filters, domain commands, resource IDs, and pagination.Authorization credentials, tracing context, locale when it is transport policy.

If a receiver must understand the value to perform the business operation, make it a typed protobuf field. Metadata keys are strings, case-insensitive, and conventionally lowercase.

Client task

Before calling Greet, create outgoing metadata with a fixed value:

"x-request-id", "practice-001"

Attach it to the same call context using metadata.NewOutgoingContext. Do this after creating the deadline context so the deadline remains part of the context chain.

Server task

At the beginning of Greet, call metadata.FromIncomingContext(ctx). Read the values for x-request-id and log them. If the key is absent, return:

status.Error(codes.InvalidArgument, "x-request-id is required")

For this exercise, a missing request ID is a deliberate validation failure. In a work service, whether a missing ID is an error is the service contract, not a universal gRPC rule.

Run both outcomes

  1. Run the client with the metadata. The server should log practice-001, then the client should receive a greeting.
  2. Temporarily remove the metadata attachment. The client should report InvalidArgument.
  3. Restore the metadata attachment.

Restore the server's immediate greeting response first. The prior three-second delay would hide the metadata result behind the deadline.

Retrieval check
