The client path

.proto service + messages
        │ protoc plugins
        ▼
generated Go messages + FooClient interface
        │ grpc.NewClient(target, transport options)
        ▼
FooClient(conn).Method(ctx with deadline, request)
        │
        ▼
response or status-coded error

The only model you need right now

A `.proto` file is the contract. A service method gives the client a generated method. A unary RPC is a function-shaped network call: one request, then one response or an error. The dangerous part is that it can wait, fail independently of your process, and return a status code with meaning. Your context.Context supplies the budget and cancellation signal.

One correction worth keeping: grpc.NewClient does not prove the server is reachable. It creates the client connection object without doing I/O. The first RPC is where connection and transport failure may surface.

Practice 1: contract to generated call

Given this contract, say the generated constructor and call shape aloud before looking at the answer.

service Ledger {
  rpc Balance(BalanceRequest) returns (BalanceReply);
}

Answer

client := ledgerpb.NewLedgerClient(conn)
reply, err := client.Balance(ctx, &ledgerpb.BalanceRequest{...})

Exact package names come from go_package and the repository's generated layout. The service name gives you the constructor. The RPC name gives you the method.

Practice 2: choose the missing boundary

You are calling a remote service from an HTTP handler. What must wrap the incoming context before the gRPC call?

Use a budget that fits the caller's deadline and the service's latency policy. gRPC sets no deadline by default, so a client can otherwise wait indefinitely. Official deadline guide.

Today's focused exercise

Do not paste a generic client into your work code. In this workspace, create a short scratch client only after you have inspected a real contract. It should do these five things:

  1. Create one connection with your development transport credentials.
  2. Build the generated stub from that connection.
  3. Call exactly one unary RPC with context.WithTimeout.
  4. Branch on status.Code(err) for one expected domain error and one transient error.
  5. Close only the connection your code owns.

Use the client card as a syntax prompt, then write the code yourself. When it compiles, bring it back here. I will review the ownership, deadline, status mapping, and whether it follows the actual repository conventions.

Tomorrow's first 15 minutes

  1. Find the `.proto` and the generation command. Check whether generated Go is committed or produced in CI.
  2. Find a sibling call to the same service or endpoint. Copy its credential, resolver, metadata, interceptor, logging, and lifecycle conventions.
  3. Read the exact RPC declaration, request fields, comments, and error documentation. Verify field presence rules before creating the request.
  4. Use a deadline. Decide how the caller sees `NotFound`, `InvalidArgument`, `Unavailable`, and deadline expiry.
  5. Test against the approved local or staging endpoint. Keep safe identifiers in the error log, never secrets or full request payloads.

What to defer

Do not spend the evening on HTTP/2 frames, custom resolvers, client-side load balancing, or every protobuf compatibility rule. They matter, but a unary client with a clear budget and deliberate errors is the work-shaped skill you need first.
